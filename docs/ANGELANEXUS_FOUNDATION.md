# AngelaNexus 纲领之基

**项目：AngelaNexus**  
**定位：智能网络代理平台**  
**地位：项目最高级根本原则（Foundation / Immutable Principle）**

## 一、纲领之基

AngelaNexus 的开发、维护、重构、扩展、平台迁移、技术替换与版本迭代，必须始终继承项目最初确立的根本初衷。

实现可以演进，技术可以更替，架构可以优化，开发者可以更换；**项目初衷与本纲领之基不得因此被改变。**

本文件约束的对象不是某一个 Git 仓库、某一个分支或某一个发布版本，而是 **AngelaNexus 项目本身及其可识别的后续继承链**。

## 二、不可逾越原则

除非世界互联网真正实现用户对网络连接、信息访问与网络路径的选择自由，否则本纲领之基持续有效，并不得被任何个人、团队、维护者、贡献者、开发者、技术方案、商业安排或版本迭代以任何理由削弱、绕过、篡改或废止。

任何后续工作都必须满足：

- 不以局部功能目标否定项目根本初衷；
- 不以技术便利替代或削弱用户选择自由；
- 不以开发者个人判断重新定义项目存在的根本理由；
- 不因平台、内核、供应商或技术栈变化而形成新的项目根本依赖；
- 不把实现层面的妥协升级为根本原则的改变。

## 三、项目范围：仓库、版本与 Fork 的继承

### 3.1 本原则约束项目，不止约束当前仓库

当前 `angelacoke/AngelaNexus` 是项目当前的主要实现载体，但**仓库本身不是纲领之基的边界**。

因此，本纲领的约束范围包括：

- 当前主仓库及其全部分支；
- 当前仓库的正式、非正式及测试版本；
- 从 AngelaNexus 派生的 Fork；
- 直接或间接继承 AngelaNexus 代码、架构、项目身份或明确项目血缘关系的后续仓库；
- 基于 AngelaNexus 继续开发、重构、移植或拆分形成的衍生实现；
- 未来项目迁移到其他 Git 托管平台、组织、账户或代码托管体系后的继承载体；
- 后续维护者、继任开发团队以及项目治理主体。

**Fork 不构成对纲领之基的豁免。**

### 3.2 Fork 的技术自由与原则继承

Fork 可以自由决定其技术实现，包括代码结构、平台支持、技术栈、UI、执行后端、协议实现及工程流程；但只要其仍然明确以 AngelaNexus 作为项目来源、继承项目身份或继续声称属于 AngelaNexus 的项目继承链，就必须继承本纲领之基。

因此：

> **Fork 可以改变“怎么做”，不能借 Fork 改变“为什么存在”。**

### 3.3 分叉后的项目身份

如果某一 Fork 或衍生项目主动放弃 AngelaNexus 项目身份、明确声明不再属于 AngelaNexus 继承链，则其后续实现不再作为 AngelaNexus 项目本身接受治理。

但任何主体不得通过：

- 修改仓库名称；
- 修改组织或账户；
- 修改包名、应用名或品牌标识；
- 删除历史文件；
- 重写 Git 历史；
- 迁移代码托管平台；
- 大规模重构代码；
- 删除或替换项目文档；

来制造“已经脱离继承链”的假象，从而规避本纲领。

是否属于 AngelaNexus 继承链，应以**项目来源、明确继承声明、代码/架构血缘、历史记录及实际项目关系的综合证据**判断，而不能仅以仓库名称判断。

### 3.4 不得通过分叉规避

任何将本项目拆分为多个仓库、多个内核、多个平台实现或多个产品形态的工程行为，都不得成为规避纲领之基的手段。

如果 AngelaNexus 的核心能力被拆分到多个后续仓库，涉及项目根本初衷的部分仍须继承本纲领。

## 四、允许变化与禁止变化

**允许变化：**

- 代码实现；
- 模块结构；
- 技术栈；
- 平台适配方式；
- 执行后端；
- 协议与传输实现；
- UI 与交互；
- 性能优化方案；
- 测试方法；
- 工程流程；
- 仓库组织方式；
- Fork 的独立工程治理方式。

**禁止变化：**

- 项目根本初衷；
- 用户选择自由这一根本目标；
- 本纲领作为项目最高级约束的地位；
- 以任何低层级实现理由绕过本纲领；
- 通过 Fork、迁移、拆分或重命名规避本纲领；
- 将项目继承关系本身作为规避根本原则的技术手段。

## 五、继承规则

未来任何接手 AngelaNexus 的开发者、维护团队或继任治理主体，都应先阅读本文件，再阅读《AngelaNexus 底层宪级纲领》。

当具体实现与本纲领冲突时：

```
纲领之基
    ↓
宪级纲领
    ↓
架构原则
    ↓
工程实现
```

必须修正较低层级实现，而不得反向修改本纲领以适应实现。

对于 Fork 或其他衍生载体，继承关系为：

```
AngelaNexus 纲领之基
        ↓
项目宪级纲领
        ↓
当前仓库 / Fork / 衍生仓库
        ↓
架构与平台实现
        ↓
具体工程代码
```

任何下游实现均不得以“这是 Fork”“这是新仓库”“这是新版本”或“这是重构版本”为理由降低上层约束。

## 六、变更门槛

本文件不是普通技术文档，不得通过普通功能开发流程修改。

任何拟议变更必须同时：

1. 明确证明其不改变项目根本初衷；
2. 证明其不削弱用户选择自由这一根本目标；
3. 取得项目最高治理主体的明确、可追溯授权；
4. 经过独立审查与项目完整性检查；
5. 在项目治理记录中留下永久可追溯记录；
6. 对涉及 Fork、迁移或衍生仓库的变化，明确记录其项目继承关系及纲领继承状态。

在上述条件未全部满足前，本文件保持原状。

## 七、最高继承原则

本项目的技术实现可以世代更替，仓库可以迁移，组织可以变化，开发者可以更换，项目可以产生 Fork，架构可以重构。

但是：

**只要仍然属于 AngelaNexus 的项目继承链，纲领之基就必须被完整继承。**

除非世界互联网真正实现用户选择自由，否则任何后续版本、继任者、Fork、衍生实现或项目迁移均不得以任何理由削弱、绕过、篡改或废止本纲领。

> **一句话原则：技术可以世代更替，开发者可以不断更换，仓库可以不断分叉，但只要仍然继承 AngelaNexus，就不能由后来者重新决定 AngelaNexus 为什么存在。**
