# AngelaNexus 纲领之基

**项目：AngelaNexus**  
**定位：智能网络代理平台**  
**性质：项目第一原则、不可逾越的最高层产品目标与架构方向基础约束**

> **本文件定义 AngelaNexus 的第一原则。它是项目的“基因”，具有最高优先级、持续有效且不可逾越。后续任何架构、代码、功能、测试、优化、平台适配、内核接入、工程决策和阶段推进，都必须以本原则为前提，不得以技术便利、局部最优、阶段性目标或实现难度为理由削弱、替换或偏离本原则。**

## 第一原则：纲领之基

AngelaNexus 的目的非常简单：

> **统一现在各类网络访问 APP 各自为政的局面，让用户在一个统一平台上，按照自己的需求，自由、灵活、安全地访问互联网。**

这不是阶段目标，不是 Android 阶段目标，也不是某一项技术实现目标，而是 **AngelaNexus 自始至终不可改变的项目根本目标**。

AngelaNexus 不是为了制造一个更复杂的代理软件，而是为了把目前分散在不同 APP、不同内核、不同配置体系和不同网络控制方式中的能力，统一到一个用户可理解、可控制、可验证的平台中。

## 一、第一原则的不可逾越性

“纲领之基”具有最高项目优先级：

1. **任何技术方案必须服务于纲领之基。**
2. **任何架构扩展都不得改变纲领之基。**
3. **任何平台实现都不得为了局部便利而缩小纲领之基规定的产品目标。**
4. **任何阶段性任务都不能把阶段目标误认为最终目标。**
5. **任何技术能力都不能因为“技术上可以实现”而自动成为项目主线。**
6. **如果实现方案与纲领之基发生方向性冲突，必须修正实现方案，而不是削弱纲领之基。**
7. **如果现有宪级纲领的细则与纲领之基发生方向性冲突，应修正细则，而不是牺牲纲领之基。**

因此，任何阶段性审计首先必须回答：

> **我们现在做的事情，是否仍然在实现“一个统一平台，让用户按自己的需求自由、灵活、安全地访问互联网”？**

如果不能明确回答“是”，则不得仅以“技术已经完成”作为继续推进的理由。

## 二、纲领之基与宪级纲领的关系

二者的关系固定为：

**纲领之基 = 项目的基因、第一原则、不可逾越的最高目标。**

**宪级纲领 = 项目的细则，用于规定如何按照纲领之基进行设计、实现、验证和约束。**

层级关系：

```
                 纲领之基
                     │
          项目的基因 / 第一原则
                     │
          不可逾越的根本目标
                     ↓
              宪级纲领
          项目的设计与实施细则
                     ↓
           架构 / 代码 / 测试
                     ↓
          真实平台 / 真实用户反馈
                     ↓
              回到目标验证
```

**宪级纲领不能凌驾于纲领之基。**

宪级纲领的职责是帮助项目实现纲领之基，而不是重新定义项目为什么存在。

如果未来出现新的技术能力、平台约束或工程问题，应当按照以下顺序判断：

1. 先检查是否符合纲领之基；
2. 再检查是否符合宪级纲领；
3. 如果违反宪级纲领但有助于纲领之基，应修正宪级纲领并记录原因；
4. 如果违反纲领之基，则不得因为技术可行而继续。

## 三、什么必须被统一

平台应逐步统一用户面对的：

- 配置与节点管理
- 协议与传输能力
- Mihomo / sing-box / Xray 等执行后端
- 规则与策略
- 路由与分流
- DNS
- TUN / 系统代理等系统网络入口
- 应用与网站级访问策略
- 链式代理
- 故障转移与恢复
- 网络状态、安全状态和运行状态
- 跨平台用户体验与控制语义

**统一的是用户体验、数据模型、策略语义、控制方式和调度方式；不是强行抹平所有底层实现差异。**

## 四、用户是网络行为的最终决定者

AngelaNexus 的“智能”首先用于**降低复杂性**，而不是替用户夺取控制权。

平台可以：

- 自动识别
- 自动分析
- 自动匹配能力
- 自动生成执行计划
- 自动选择符合用户授权范围的执行 Driver
- 自动检测故障
- 自动恢复

但涉及用户网络行为的重要决定，必须保持：

- 可见
- 可解释
- 可调整
- 可撤销
- 可限制
- 可固定

用户可以按需决定自己的网络访问方式。

## 五、一个平台承载多种执行能力

用户不应因为底层执行后端不同而被迫安装、切换多个 APP。

Mihomo、sing-box、Xray 等应作为 AngelaNexus 的执行能力接入统一平台：

```
                     AngelaNexus
                          │
                  Unified User Intent
                          │
                  Policy / Capability
                          │
                   Execution Plan
                          │
             ┌────────────┼────────────┐
             ↓            ↓            ↓
          Mihomo       sing-box       Xray
             └────────────┼────────────┘
                          ↓
                    Internet Access
```

三内核是实现统一平台目标的手段，而不是产品目标本身。

## 六、按需访问是核心使用模型

“按需”意味着平台应允许用户表达并执行类似需求：

- 某些流量直连
- 某些流量代理
- 某个应用使用指定路径
- 某个网站使用指定节点或策略
- 某类协议使用能够执行它的 Driver
- 某些流量采用链式代理
- 某些能力允许自动故障转移
- 某些能力由用户固定
- 某些功能明确关闭

平台的职责是**准确执行用户意图**，而不是建立一个不可理解的“自动替用户决定网络”的黑箱。

## 七、复杂性应该被平台吸收

用户不应该为了实现一个简单的网络需求而理解：

- 哪个 APP 使用哪个内核
- 哪个配置格式属于哪个客户端
- 哪个协议只能在哪个软件运行
- 哪套规则应该复制到哪个 APP
- DNS 应该在哪个软件里设置
- TUN 应该在哪个 APP 里打开
- 某个节点为什么必须转换成另一种格式
- 不同 APP 之间为什么行为不一致

这些复杂性应该逐步由 AngelaNexus 的统一模型、能力注册、策略系统和 Driver 调度吸收。

**用户看到的是需求和结果，平台承担底层复杂性。**

## 八、底层能力必须服务于产品闭环

所有底层技术最终必须服务于：

```
用户需求
   ↓
导入网络资源
   ↓
统一识别与规范化
   ↓
用户策略
   ↓
能力匹配
   ↓
执行 Driver
   ↓
实际网络访问
   ↓
安全 / 正确性验证
   ↓
持续运行
   ↓
故障恢复
```

任何新模块、新抽象、新探测机制或新优化，如果不能直接帮助这个闭环，则不得仅因为技术上“可以做”就继续扩张。

## 九、三内核的正确定位

Mihomo、sing-box、Xray 必须保持平行能力关系。

平台不应围绕“哪个内核最重要”建立产品结构，而应围绕：

**Intent + Policy + Capability + Driver**

进行统一调度。

原则为：

> **平台统一意图，能力负责匹配，Driver 负责翻译，内核负责执行。**

同一网络 Session 不应无理由同时由多个内核承担；链式代理等明确的多阶段 Pipeline 除外。

## 十、跨平台的真正意义

Android、iOS、Windows、macOS、Linux 的目标不是让五套 APP 各自复制一遍功能。

真正目标是：

> **一套统一的平台语义，在不同操作系统上调用各自正确的系统能力。**

平台核心保持统一；操作系统差异由 Platform Abstraction Layer 吸收。

**Android 是第一完整落地平台和真实试验田，但不是架构中心，也不是功能精减版。**

Android 的职责是首先把完整的 AngelaNexus 用户闭环落到真实设备和真实网络环境中，以真实运行数据和用户反馈验证平台方向；经过验证的能力再沉淀回统一跨平台核心。

因此：

- Android 不等于整个架构
- Android 试验田不等于 Android 功能阉割
- Linux 内核不等于第四个代理内核
- Windows 系统代理不等于平台策略
- macOS / iOS Network Extension 不等于核心业务
- 各平台原生能力应服务统一用户意图

## 十一、工程范围的最高约束

AngelaNexus 应当**解决问题，而不是制造新的复杂度**。

当出现新的技术问题时，优先顺序必须是：

1. 是否直接阻塞用户按需访问互联网？
2. 是否直接影响安全、正确性或稳定性？
3. 是否可以用已有能力解决？
4. 是否必须增加新的抽象？
5. 新抽象是否会产生新的长期维护负担？

如果问题可以在现有边界内解决，不得为了“架构完整”而继续增加层级。

如果问题确实阻塞核心闭环，则必须真实解决，而不能用 Mock、占位接口、虚假状态或“看起来完成”的实现绕过。

## 十二、真实实现与真实验证

“实现”必须以用户实际可用为标准，而不是以代码存在或 CI 通过为标准。

核心闭环必须逐步达到：

**用户需求 → 导入 → 识别 → 用户决定 → 能力匹配 → 三内核调度 → 真实连接 → 流量接管 → 安全验证 → 正常访问 → 持续运行 → 故障恢复**

其中任何关键环节如果仍是：

- Mock
- Placeholder
- 固定返回成功
- 虚假的运行状态
- 仅有接口而没有实际执行
- 仅有 CI 而没有真实运行证据

都不能宣称该环节已经完成。

CI 是必要验证，但不是完整验收标准；真实平台运行和真实用户反馈同样属于产品验证闭环。

## 十三、最终判断标准

AngelaNexus 的最终成功标准不是：

- 模块数量
- 抽象层数量
- 探测能力数量
- 技术名词数量
- 代码规模

而是：

> **用户是否可以在一个平台上，以统一、清晰、可控的方式，根据自己的需要使用现有的各种网络访问能力，而不再被不同 APP、不同内核和不同配置体系人为割裂。**

因此，任何阶段性实现都必须最终回到三个问题：

### 1. 用户能不能更方便地按需访问互联网？

### 2. 用户能不能在一个平台上统一管理原本分散的网络能力？

### 3. 平台有没有在统一的同时保留用户对网络行为的最终控制权？

如果答案是否定的，则应重新审视该实现是否仍然服务于 AngelaNexus 的根本目标。

## 十四、阶段执行与双层审计

以后每一个实现步骤，都必须进行两层校验：

### 第一层：纲领之基校验

确认：

> **有没有偏离项目第一原则？**

重点检查：

- 是否仍在推动统一网络访问平台；
- 是否仍在扩大用户按需访问能力；
- 是否仍由平台吸收复杂性；
- 是否仍保留用户最终控制权；
- 是否产生与根本目标无关的技术扩张。

### 第二层：宪级纲领校验

确认：

> **实现方式有没有违反既定工程细则？**

包括架构、安全、三内核、跨平台、资源、权限、验证、反投毒、防入侵等约束。

只有：

> **纲领之基通过 + 宪级纲领通过 + 实际验证通过**

才能进入下一阶段。

如果发现偏离：

**停止推进 → 定位偏离 → 修正 → 重新验证 → 再继续。**

## 十五、不可逾越条款

以下条款作为 AngelaNexus 项目第一原则的永久约束：

> **第一：纲领之基不可被阶段目标替代。**

> **第二：纲领之基不可被任何单一平台、单一内核或单一技术路线替代。**

> **第三：不能为了实现方便而削弱用户按需访问互联网的最终目标。**

> **第四：不能为了技术复杂度而牺牲统一平台的产品目标。**

> **第五：不能以“看起来完成”替代真实实现。**

> **第六：宪级纲领服务于纲领之基；若二者发生方向性冲突，修正细则，不牺牲根本目标。**

> **第七：任何后续开发、审计、重构、优化和平台扩展，都必须首先回到纲领之基进行判断。**

---

## 核心定义

> **AngelaNexus = 一个统一承载多种网络访问能力、由用户按需控制、由平台负责复杂性、跨平台运行的智能网络代理平台。**

> **技术服务于这个目标，而不是目标本身。**

> **纲领之基是项目的基因；宪级纲领是项目的细则。**

> **基因不可逾越，细则必须服务于基因。**
