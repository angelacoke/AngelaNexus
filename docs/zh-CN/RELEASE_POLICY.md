# AngelaNexus 发布策略

## 1. 发布原则

AngelaNexus APP **不会从正式版 / Stable 起步**。

早期公开发布明确属于非正式版本，必须使用清晰的预发布标识。

构建成功、APK/AAB 已签名或 CI 全绿，都不能单独证明已经达到正式版或生产就绪标准。

## 2. 发布生命周期

```text
开发阶段
   ↓
Alpha / 实验版
   ↓
Preview / 预览版
   ↓
Beta / 测试版
   ↓
Release Candidate / 候选版
   ↓
Stable / 正式版
```

每个阶段可以根据实际验证结果持续足够长的时间，不得为了赶进度强行升级版本阶段。

## 3. 当前 APP 状态

当前 Android APP 版本基线为 `0.1.0`，明确属于**开发/非正式版本**，不得宣传或标记为 Stable / 正式版。

## 4. 各阶段要求

### Alpha / 实验版

目标：验证架构、核心流程、集成边界以及早期真实设备行为。

必须满足：

- 明确标注非正式版本
- 记录已知限制
- 不宣称正式版或生产就绪
- 适用范围内的自动化构建和测试通过
- 不支持的能力必须安全失败

### Preview / 预览版

目标：验证更完整的用户工作流和平台集成。

必须满足：

- Alpha 阶段主要回归问题已经处理或明确记录
- 核心导入/配置流程完成验证
- 能力识别和 Driver 调度完成验证
- 支持范围内的基础安全与防泄漏检查通过
- 代表性设备上的资源行为已经测量

### Beta / 测试版

目标：进行更广泛的兼容性和产品行为验证。

必须满足：

- 主要回归测试通过
- 扩大真实设备测试范围
- 已声明功能对应的三内核能力/一致性验证通过
- 网络生命周期和故障处理完成验证
- RAM、CPU、后台唤醒、电池消耗已有测量数据
- 升级和配置迁移行为完成验证
- 已知限制明确记录

### Release Candidate / 候选版

目标：验证指定构建是否具备进入正式版评估的条件。

必须满足：

- 不存在已知的发布阻断问题
- 发布产物和签名验证通过
- 支持范围内的安全和防泄漏验证通过
- 资源回归已经审计；任何接受的回归必须有明确依据
- 声明范围内的真实设备验证完成
- 发布说明和已知限制确定
- 在适用情况下完成回滚/恢复验证

### Stable / 正式版

Stable 是独立的工程状态，而不仅仅是修改版本号。

只有当项目已经获得足够证据证明声明范围内的功能可靠、安全、资源效率合理、可维护且可重复验证时，才能正式进入 Stable。

## 5. 发布门槛

每个候选版本必须检查：

- 功能正确性
- 回归稳定性
- 安全性
- 防泄漏
- 协议/传输一致性
- Driver 能力匹配
- 真实设备行为
- 跨平台支持范围
- 内存使用
- CPU 使用
- 后台唤醒
- 电池消耗
- 网络控制开销
- 签名和发布产物完整性
- 升级与迁移行为
- 已知限制

任何无法解释或不可接受的发布关键指标回归，都必须阻止进入下一阶段。

## 6. 版本语义

版本号本身不得被视为 Stable 状态的证明。

非正式状态必须通过发布渠道、Release Notes 以及支持的平台发行元数据明确体现。

## 7. 核验规则

进入下一发布阶段前，必须重新核验上一阶段的必要门槛。

如果验证失败或停滞，必须先调查、修复并重新核验，再继续推进：

```text
核验
 ↓
审计
 ↓
修复
 ↓
重新核验
 ↓
推进
```

## 8. 用户可见的发布诚实性

AngelaNexus 必须明确区分：

- 开发版
- Alpha / 实验版
- Preview / 预览版
- Beta / 测试版
- Release Candidate / 候选版
- Stable / 正式版

非正式版本不得使用 Stable、production-ready、final 或具有相同含义的表述。
