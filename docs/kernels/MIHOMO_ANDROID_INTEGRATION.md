## Integration boundary

AngelaNexus owns lifecycle, configuration transport, VPN/TUN ownership, security policy, ABI validation and runtime status. Mihomo owns packet processing and native networking operations. Configuration parsing and kernel selection remain in AngelaNexus Core; the bridge must not duplicate them.

The Android integration requires no implicit runtime fallback, no loading of unverified artifacts, and no native capability claims before the corresponding real smoke test succeeds. New JNI consumers require the error-returning `angelaStopTun` export; an older library without it fails explicitly rather than reporting a successful stop.

## What TUN stop actually guarantees

The bridge serializes configuration, TUN lifecycle and explicit suspend/resume. Stop first suspends tunnel admission, closes the socket-protection gate, waits for already-entered protection callbacks to return, and closes the bridge-owned TUN listener. A failed listener close retains ownership for retry; the protection gate stays closed. Configuration cannot restore readiness inferred merely from a retained listener, and explicit resume cannot reopen an unattached or failed-stop runtime.

Before the listener close attempt, stop closes ordinary tunnel tracker registration and advances its generation. After the listener close attempt, stop snapshots the pinned upstream's `statistic.DefaultManager` and attempts to close every visible TCP/UDP tracker, even when the listener close failed. Listener and connection errors are combined and reach JNI's existing failed-stop path. The adapted real trackers now unregister only after successful or closed-only underlying cleanup; genuine failures remain visible in the manager. The bridge also retains failed tracker ownership independently and retries it on the next stop or replacement start. Successful cleanup entries are removed rather than closed again by an empty repeated stop. Configuration updates do not sweep active connections.

A captured socket may already have been closed by a concurrent upstream worker. A close error consisting only of the standard `net.ErrClosed` (including wrapped/joined closed-only errors) counts as released rather than becoming a permanently failing retry. A joined error containing any unrelated failure remains pending and is reported; an empty tracker list alone is never used as proof of socket closure.

The admission read lock spans only the socket protection callback. Stop/configuration do not hold the write lock while invoking upstream cleanup/configuration, which may itself invoke the hook. Stop waits for an in-progress `VpnService.protect` call; this is not a timed cancellation mechanism and does not promise a fixed shutdown deadline.

Each socket hook samples an admission epoch before checking readiness or waiting for the read lock. Every stop/configuration drain invalidates the previous epoch before acquiring the write lock. A hook paused before acquiring its read lock cannot borrow a later reopened `protected=true` state after configuration or replacement; it is rejected before touching the socket or invoking protection. This protects hook admission only, not a dial that has already returned successfully from the hook. Epoch tokens do not tag upstream tracker registrations or cancel ongoing connects.

The same closed-only error rule also applies to the TUN listener: `net.ErrClosed`, including wrapped/joined closed-only errors, releases its retained ownership. Any mixed real failure still reaches the retry path. This does not classify arbitrary close errors or error strings as successful cleanup.

Configuration parsing is part of the lifecycle critical section, not a read-only preparation step. At the pinned upstream revision, `config.Parse` temporarily changes global settings and later rolls them back; parsing outside the mutex can race another apply/DNS update or restore stale settings after it. The exported configuration body now holds `androidTunMu` through parse, apply and saved-JSON commit. Home-directory initialization takes the same lock, as do DNS reconfiguration and stop/start. Parse rejection does not replace the saved configuration. This serializes bridge control calls only: it neither synchronizes every upstream background reader nor cancels an in-progress parse, and stop can wait for parsing/application to return.

### Stop admission before the control-lock wait

A stop request now increments a pending-stop counter and closes/drains socket-hook admission **before** waiting for `androidTunMu`. A parser or apply already holding that mutex may still finish, but cannot restore admission over a queued stop. Readiness restoration takes the admission write lock, so a paused restore cannot publish stale readiness after the stop's callback barrier returns. Hook checks, configuration resume, TUN startup and explicit resume all account for pending stops; multiple callers retain separate requests until their own cleanup attempt returns, including error paths. Resource ownership and listener/tracker cleanup remain under the control mutex. A replacement checks for pending stops before duplicating or consuming the caller's descriptor; if stop arrives during construction, the queued stop owns cleanup and socket admission remains blocked.

This is a callback-admission barrier, not a synchronous parser cancellation or a dial-completion barrier. A hook which completed before the stop barrier can still lead to a late connect/registration. Stop still waits for an ongoing parse/apply and individual upstream close operations; no stop deadline, complete background-task shutdown or physical-device leak/battery result is claimed. During that wait, tunnel status may reflect the operation holding the control mutex; it is the hook gate, not that status, which rejects new socket admission.

Deterministic host tests hold the real control mutex and queue one or two calls to the actual stop body, check protection is never invoked for a new hook while cleanup waits, and verify listener ownership, combined error/retry behavior and resume rejection. Helper tests also drain an in-progress protection callback and race readiness restoration against stop. The previous stop body fails the queued-stop regression. Holding the mutex models the wait imposed by parse/apply; these tests do not inject or cancel a slow upstream parser.

**This is not full Mihomo shutdown.** A connection whose socket hook returned before stop may still finish dialing after the snapshot. The ordinary tunnel TCP/UDP paths now reject and close those late results at their generation-aware tracker registration boundary, as described below. Other tracker constructors, unregistered connections, NAT state, provider health checks/fetchers, DNS listeners and other upstream goroutines are not all covered. The default statistics sampler has the separate joined-stop contract below. The snapshot is not a dial-completion barrier or a guarantee that every connection present at stop entry was observed. At the pinned revision, `executor.Shutdown()` is also not a complete connection/task termination API, so calling it would not establish that guarantee. A successful TUN stop must not be presented as proof of zero remaining sockets, background work or battery use. Individual upstream close operations have no new timeout.

A replacement TUN start attempts the same listener/tracker cleanup before validating all new arguments; any cleanup failure prevents constructing the new TUN and retains the caller's descriptor. Even an invalid replacement therefore closes captured old connections and can leave the runtime stopped. Only a successful new TUN construction reopens protection and resumes admission.

## What the tests establish

- Go helper tests with the race detector exercise protection rejection, callback draining during stop/configuration, panic-safe lock release, close failure/retry, joined connection errors, duplicate-ID ownership and idempotence.
- A host cgo test against the pinned upstream source exercises actual `executor.ApplyConfig` and tunnel status transitions. It also registers real loopback TCP/UDP sockets with upstream trackers, carries data before stop/replacement, and checks underlying socket closure (including peer EOF), not merely an empty manager. An injected underlying close failure proves retry survives upstream unregistration and a simultaneous listener failure. Only the Android build constraint is removed from the bridge; the whole dedicated library package is tested, while importing the real upstream core packages. CI restores the original bridge before NDK compilation. Loopback sockets are deliberately created with Go's `net` package, not the protected dialer. This is not Android SDK, TUN, VPN protection, full routing or full-core shutdown evidence.
- Package integration tests reject upstream CLI flags and invoke the installed socket hook, including the actual cgo fail-closed path when no host VpnService symbol exists. A separate host `c-shared` build is loaded through `ctypes` with foreign host arguments; it exercises C result ownership, initialization, invalid/valid configuration, invalid TUN start, repeated stop and reconfiguration. The process has a 30-second outer timeout. This proves host ABI callability, not valid Android TUN attachment or process-wide quiescence.
- Concurrent host regressions call the same bodies as the C exports for apply, DNS update, home initialization and stop; they verify saved/upstream mode agreement and that an unattached runtime stays suspended. Rejected configurations preserve committed state. Restoring the old parse-outside-lock boundary produces actual race-detector failures. The real `ctypes` smoke also calls those four C exports from multiple host threads with result ownership checks; this does not establish thread safety for all upstream background tasks.
- Three-ABI NDK builds check every required exported symbol and record artifact, bridge, lifecycle and library-entry SHA-256 provenance plus the dedicated build package.
- Ordinary `android-build` prepares Xray/sing-box AARs. Passing that workflow alone does not prove it included the latest Mihomo `.so` or executed `angelaStopTun`.

## Explicit pause and resume

The exported `suspend(1)` closes new socket-hook admission with a separate pause flag, invalidates pre-pause epochs and drains already-entered protection callbacks before returning. Suspending tunnel ingress alone is insufficient: background dialers can still reach the socket hook. Reconfiguration preserves explicit pause. `suspend(0)` clears only pause, cannot invent readiness after stop/failed attachment and cannot override queued stops. A successful new TUN attachment retains the prior startup behavior of starting unpaused; a failed attachment does not clear pause.

Pause now announces a counted request and closes/drains hook admission **before** waiting for the control mutex, just as stop does. An already-running resume, configuration or start cannot bypass queued pauses, even if it clears the pause flag or restores protection ownership. Each queued pause reasserts its final paused state under the control mutex and retires its request before releasing that mutex, so a following explicit resume cannot mistake a completed request for an outstanding pause. Multiple pause callers retain independent requests. Pause does not close or discard the listener or existing connection ownership.

Final pause/resume state remains serialized with configuration and listener changes. There is no parsing/application/protector deadline, dial-completion barrier, existing-socket close, late-registration barrier or background-task shutdown here. During the control-lock wait, tunnel status can still reflect the operation holding that lock; the socket-hook gate is the early protection. The synchronous protection callback must not re-enter lifecycle exports while holding its hook's read-side barrier. Host helper/bridge tests cover one or two queued pauses, attempts to resume/restore admission while they wait, protection callback draining, stale entries, reconfiguration and failed replacement. The previous exported pause body fails the queued-pause regression; concurrent ctypes calls establish export callability, not Android TUN acceptance.

## Dedicated shared-library entry

The shared library no longer builds the upstream module root: its CLI `main.go` registers and parses process arguments in `init()`, an inappropriate side effect for an embedded runtime. The dedicated `main()` is empty; runtime startup remains explicit through the bridge exports. Imported core package initialization can still create upstream background tasks; the bridge explicitly stops the default statistics sampler during its own initialization.

This replaces the earlier mismatch where host tests excluded CLI startup with an explicit file list but NDK builds still compiled the module root. The pinned upstream revision is unchanged; only the reviewed owned-FD and statistics adaptations are applied by `prepare-upstream.py`, with exact pristine/patched source and patch digest checks. The packaging verifier rejects absent/mismatched package or entry evidence, so historical root-package builds cannot silently satisfy the new contract. Runtime hashes and distribution approvals still require separate review; this change does not authorize packaging a new library.

## Joined statistics sampler stop

The default manager's one-second sampler now exposes idempotent `StartStatistics` and synchronous `StopStatistics`. Start/stop share a lifecycle mutex; stop closes the worker signal and waits for its completion before allowing a restart. The ticker is stopped before completion is published. This is a worker join, not a goroutine-count estimate or a sleep-based cleanup assumption.

The bridge stops the imported sampler during initialization and after every listener cleanup attempt, including failed stop and invalid replacement. Only a successful committed attachment restarts it. Configuration and explicit pause/resume do not start a sampler on an unattached runtime; pause on an attached runtime intentionally leaves it running. Cleanup still waits for the control mutex, listener close and protection callbacks; no new stop deadline is promised.

Stop clears instantaneous upload/download rates but preserves total and pending byte counters. A later attachment resumes sampling pending bytes. Those first resumed values can therefore include traffic accumulated while stopped; they are interval counters, not proof of continuous one-second wall-clock throughput across the gap. Tracker registration and counter writes are not blocked by stopping this sampler.

Native package tests observe the completion channel and serialize competing lifecycle calls, and the bridge tests exercise real sampling across stop, failed listener cleanup, invalid replacement and synthetic successful reattachment. The build records `statistics.patch` and patched `tunnel/statistic/manager.go` digests; packaging rejects missing/mismatched statistics evidence as well as the existing ownership-adapter evidence. This closes only the default sampler worker/ticker. Provider health checks/fetchers, DNS, dial completion, late registrations and UDP/NAT workers remain separate unresolved lifecycle work; no device leak/battery or current-library packaging claim follows.

## Reject configuration work superseded by stop

Configuration and DNS-update requests now capture a dedicated stop generation before waiting for `androidTunMu`. They reject immediately while any stop is pending, then recheck the captured generation and pending-stop count after acquiring the control lock. This second check is the operation's execution-admission boundary. A request still waiting when stop is announced cannot begin its configuration transaction; even if all stops finish before it acquires the lock, the changed generation rejects that stale request. Each stop advances the generation independently. The rejection reaches callers as an explicit error; it never replaces `lastConfigJSON` or silently reports success. A genuinely new request after stop completes can configure the still-unattached runtime without inventing TUN readiness.

This is deliberately **not cancellation of an admitted operation**. An operation whose final check succeeds is allowed to complete parsing, application and saved-JSON commit if stop is announced afterwards, including the small interval before the actual `config.Parse` call. Stop still gates socket hooks immediately and waits for the control mutex. There is no post-parse rejection: parsed upstream configurations can own resources, so abandoning them without a complete ownership/cleanup contract would create another leak risk. Stop generation is separate from the socket-hook epoch, which is also changed by configuration and pause; those non-stop transitions must not invalidate unrelated queued configuration requests.

Deterministic helper tests cover multiple pending stops, stale generations after the count returns to zero and fresh requests. Pinned-upstream host tests exercise both real config/DNS entry bodies while the control mutex is unavailable, and both generation-carrying bodies after a completed real stop. They verify saved JSON/upstream mode remain unchanged and fresh retries commit without resuming an unattached tunnel. Disabling the four new entry/lock checks makes the pending-stop test time out and both completed-stop cases incorrectly succeed. The concurrent c-shared smoke allows only the exact stop-rejection message, only for config/DNS calls during concurrent execution; fresh sequential retries must succeed and unrelated errors still fail the test.

Local validation: 1,202 JavaScript tests; 20 helper race repetitions; 20 pinned-upstream bridge race repetitions; host c-shared foreign-flag/multithreaded export smoke; positive/negative traffic smoke for all three kernels. These are host results, not Android TUN or latest-native-artifact packaging acceptance. Complete dial exit, late/unregistered trackers, DNS/provider/NAT/statistic background shutdown, cancellation/deadlines and physical-device leak/battery testing remain unresolved. Upstream pins, approved native hashes, license/source/naming/distribution gates are unchanged.

## Reject TUN starts superseded by stop

The `startTUN` export now captures the stop generation before converting its string arguments or waiting for the control mutex. A pending stop rejects the request immediately with the existing false/zero result. The shared Go startup body rechecks that captured generation under `androidTunMu`, before suspending the tunnel, cleaning up current resources, validating startup arguments, duplicating the caller's descriptor or constructing a listener. A completed stop therefore invalidates older queued starts even after its pending count returns to zero. Rejected starts neither consume the caller's descriptor nor close a newer listener or tracker. JNI signature and result ownership are unchanged.

The startup path also rechecks immediately before duplicating the descriptor and after successful listener construction. The post-construction check is the commit boundary: it precedes releasing the caller's descriptor, clearing pause and restoring admission. A stop announced during construction therefore makes startup return false without consuming the caller's descriptor. The new listener is retained before this check, then cleanup is attempted; failed listener/tracker closes retain retry ownership for the queued or a later stop. This is rejection of a stale completion, not cancellation of construction: stop still waits for the constructor and individual cleanup operations. A stop announced after the commit check can still race with a successful return and owns queued cleanup. Fresh starts keep the existing replacement and unpaused-success contract.

Host regressions reject the actual export while the control mutex is held and stop is pending. Explicit stale tokens model queued requests after a completed stop and check that newer listener/tracker ownership, admission/pause state and a real caller-owned pipe descriptor remain intact; fresh tokens still reach normal replacement cleanup. Removing the startup generation checks reproduces both regressions. The host shared-library smoke includes invalid starts alongside concurrent configuration, DNS, initialization, stop and pause/resume calls from six foreign threads. No successful Android TUN construction, complete dial exit, late-registration barrier, background shutdown or device leak/battery result is established by these tests. Native artifact hashes, upstream pins and all packaging/license/distribution gates remain unchanged.

Additional host tests use a per-call constructor on the actual startup body, never a mutable global factory. Real pipe descriptors verify that a stop queued during construction rejects commit, leaves the caller's descriptor usable, releases the duplicate after successful cleanup and retains it after failed cleanup until retry succeeds. A fresh successful construction still consumes only the caller's descriptor and retains the duplicate until stop. Removing only the post-construction check makes both stop-during-construction cases incorrectly report success. These synthetic constructors exercise bridge ownership, not real Android TUN construction or upstream cancellation.

## TUN descriptor zero is not a usable upstream handoff

The pinned `sing_tun.New` treats `FileDescriptor == 0` as the absence of an externally supplied descriptor. Plain `Dup` can return zero when stdin is closed, so duplicating a valid VpnService descriptor that way can accidentally select upstream's create-a-TUN path instead of attaching the supplied device. Startup now uses `F_DUPFD_CLOEXEC` with a minimum descriptor of 3. The duplicate cannot collide with any standard descriptor and is marked close-on-exec atomically, without a separate inheritable window. The caller's descriptor is neither modified nor consumed before successful construction and the existing stop-generation commit check.

A host regression closes stdin only in isolated test subprocesses. Both synthetic constructor success and pre-adoption failure check the actual startup body's descriptor is >=3 and has `FD_CLOEXEC`; success verifies pipe data, caller release and stop cleanup, while failure verifies caller retention and unused-duplicate release. The previous `Dup` implementation fails deterministically by handing descriptor zero to the constructor. This exercises bridge ownership with real pipe descriptors, not Android TUN construction or actual upstream failure cleanup.

A separate ownership risk was identified here: upstream's partial constructor failure can perform its own cleanup, so closing the duplicate number again in the bridge can close an unrelated descriptor that has reused that number. The closed-stdin test alone does not establish safety for this path. The explicit ownership adaptation below supersedes that error-path behavior. Late dial/tracker registration, full background shutdown, cancellation and physical-device acceptance remain unresolved.

## Constructor failure consumes the duplicate exactly once

The bridge now requires `sing_tun.NewWithOwnedFD`, supplied by the checked-in `native/android/mihomo-bridge/prepare-upstream.py` adaptation of the same pinned Mihomo source. The adapter checks the pinned source and dependency contract before editing; an incompatible source fails preparation instead of silently building. The original upstream `New` interface retains its existing ownership behavior. The new entry accepts only the supported supplied-descriptor path and takes ownership of the duplicate for both success and error returns. Before TUN adoption, its guard closes the duplicate on failure; after adoption, the listener owns cleanup. The bridge never closes that number after the constructor returns an error. Checking `Fstat` before a second close would not be safe because descriptor numbers can be reused between the check and close.

Isolated host regressions cover consuming synthetic failure, real upstream DNS validation failure before adoption, and real upstream unknown-stack failure after adoption. Every constructor must have closed its duplicate before returning an error. The test then deliberately reuses that exact number for an unrelated pipe before returning to the bridge, and verifies both the caller-owned pipe and the reused pipe still carry data after rejection and after a subsequent stop. Existing successful-start, closed-stdin/CLOEXEC and stop-during-construction cases remain in the same pinned-upstream host package. These are descriptor ownership tests, not successful Android TUN routing, general panic recovery, full-core shutdown or device acceptance.

Native provenance now records and verifies both the adapter script digest and the adapted upstream source digest, in addition to the existing bridge/lifecycle/library-entry evidence. The upstream revision, dependency versions, packaged library hashes, licensing requirements and release gates are not relaxed. Newly built libraries still require the separate packaging and physical-device verification process; this change does not install or release them.

## Ordinary tunnel late-result registration gate

The fixed upstream adapter adds a generation-aware registration boundary for the ordinary TCP and UDP handlers in `tunnel/tunnel.go`. Each handler captures the manager's monotonically advancing registration epoch at entry, before metadata handling or dialing. Its successful dial result must atomically pass `JoinAtEpoch` before becoming a usable tracker. Closing registration and joining a tracker share a registration mutex, so a result either registers before closure and is eligible for the subsequent cleanup snapshot, or is rejected and closed outside that mutex. Merely comparing an epoch before an ordinary `Join` would leave a check-then-register race and is not this contract.

The embedded bridge closes registration during initialization and at the beginning of every cleanup attempt under `androidTunMu`, before invoking listener cleanup. A failed listener close and an invalid replacement leave registration closed. Only a committed successful attachment reopens it. Stop/replacement advance the epoch; reopening never resets it, so a previous runtime's late result cannot borrow a new attachment's admission. Pause/resume and configuration do not independently reopen registration or change its generation. The early socket-hook stop barrier remains separate: tracker closure occurs after acquiring the control mutex, not at the instant a stop is queued.

A rejected result is not returned to TCP forwarding or the UDP relay setup. Its close is performed without holding the registration mutex, because connection cleanup may re-enter upstream code. A genuine close failure, including a joined `net.ErrClosed` plus an unrelated failure, retains cleanup ownership for a future stop/replacement. A failure arriving after stop has already returned cannot retroactively change that stop's return value; it is not evidence of synchronous full cleanup. Successfully closed results are not retained for repeated close attempts.

This gate does **not** join or impose deadlines on ongoing dials, metadata resolution, handshakes or their underlying socket activity. TCP now registers each successful retry candidate before its early-data handshake, as detailed below; rejection cancels only that handler's retry context, not all runtime dials. Existing generic tracker constructors remain compatible and are not made generation-aware; DNS-internal proxy trackers, raw DNS connections, provider fetches/health checks, UDP/NAT state and other kernel workers require separate work. An old UDP setup may still own NAT state even when its late packet connection is rejected. No claim of zero live sockets or zero background activity follows from this milestone.

`late-connections.patch` is separately digest-pinned and records exact final manager, tracker and tunnel source hashes. The original statistics patch digest and its intermediate output digest remain pinned; final build evidence describes the manager after both patches. Preparation and packaging reject missing or altered patch/output provenance. This does not update historical `.so` hashes, authorize installation of the new build, relax licensing review or replace physical-device TUN, leak and battery acceptance.

The manager package regressions exercise real loopback TCP/UDP sockets, closed/current/old generations, concurrent join-versus-stop, re-entrant tracker `ID`/`Close` callbacks and mixed close-error ownership. Separate tests invoke the actual `handleTCPConn` and `handleUDPConn` bodies with a channel-blocked proxy: stop/reopen occurs while the proxy is still waiting, then the old result is released. TCP's peer sees closure without forwarded payload; the UDP result is closed with neither relay reads nor writes. Fresh-generation controls transfer real bytes through both handlers. These tests use host pipe/loopback sockets, not an Android TUN. Restoring just the two original handler registration paths fails both stale-result regressions.

Actual bridge-body tests cover successful stop, failed listener stop, invalid replacement and synthetic committed restart; they also prove that a late rejected connection's genuine close failure reaches the next stop and its retry path. CI lists and requires matching test names before execution so a missing or empty `-run` selection cannot count as this evidence. Preparation applies the patch exactly once; no second unchecked workflow patch step is permitted.

### TCP early-data admission and real tracker close retries

Each successful ordinary TCP dial result is now wrapped by `NewTCPTrackerAtEpoch` inside the retry callback, before `NeedHandshake` or the first payload write. Rejected results transfer ownership to the existing rejection cleanup, cancel only that handler's retry context and cannot send peeked bytes. Every retry candidate gets one tracker; the final relay reuses it rather than wrapping/counting the same bytes again. The pinned sing `common.Cast` follows `tcpTracker.Upstream()`, so early-handshake detection remains effective after wrapping. Actual bytes written through the tracker provide upload accounting, including partial failed writes. Existing REJECT-chain retry semantics are retained.

Both real TCP and UDP trackers now call the underlying `Close` before unregistering. Nil or exclusively wrapped `net.ErrClosed` results remove registration; genuine failures, including mixed closed/sentinel errors, leave the tracker discoverable for another cleanup attempt. This also covers failed handshake candidates and repeated cleanup of rejected late results, not only synthetic trackers. The reviewed late patch, exact tracker/tunnel output digests and adapter digest change together; previous or tampered native evidence remains invalid. No historical packaged-library hash or upstream/dependency version changes.

This is an admission boundary before early payload, not general cancellation or a write deadline. A candidate admitted before stop may still be doing handshake work while stop closes it; individual close/handshake operations may block. DNS/provider work, dial joining and full UDP/NAT shutdown remain outside this change. In particular an old same-key UDP NAT sender can still be reused across stop/reopen until epoch ownership and conditional table cleanup are implemented; do not treat tracker isolation as complete UDP-session isolation. Current `.so` packaging, physical-device TUN/leak/battery acceptance and all license/provenance/distribution approvals remain separate release gates.

## TUN UDP same-key generation and cleanup ownership

TUN UDP sender keys now include the statistics registration epoch captured at handler entry. A new TUN generation using the same client address cannot enqueue into the previous generation's sender while an old UDP dial is still pending. Rejected old results retain the existing tracker close/retry ownership contract. This is deliberately limited to `C.TUN`: non-TUN inbound keys remain the original local-address string because the TProxy write-back implementation uses that exact key to access local sockets and creation locks. Prefixing all inbound keys would break those lookups.

Both failed-dial removal and receive-loop cleanup now compare the owning sender under a single per-key `xsync.Map.Compute` operation. Receive-loop cleanup first detaches only that sender's entry, then snapshots and closes its local UDP sockets outside the table lock. An old cleanup therefore cannot delete a replacement entry or close its sockets by looking up the reused key. No socket close, logging, or arbitrary callback is performed inside the table's compute callback. The five reviewed patch sources (statistics manager/tracker, tunnel handler, NAT table and UDP connection handler) are individually pinned and included in build provenance; missing or mismatched NAT/connection evidence is rejected before packaging.

This does **not** complete all NAT or kernel shutdown. Non-TUN/TProxy sessions still have their pre-existing bare-key lifecycle and no general cross-generation namespace. A local-socket creator that already captured a detached entry is not joined, and local-socket close remains upstream-style best effort rather than a retained retry queue. Pending dials, already-admitted relay activity, DNS/providers and background worker exit still require separate cancellation/draining work. Host socket and mapping regressions do not demonstrate privileged TProxy interception or physical-device Android TUN, leak or battery acceptance. Existing upstream/dependency pins, packaged native hashes, licensing approvals and distribution gates remain unchanged; this change alone does not authorize merging, replacing packaged `.so` files or release.

## Cancel ordinary tunnel setup dials on registration stop

This milestone supersedes the earlier statement that ordinary TCP/UDP setup dials have no runtime cancellation. The statistics manager now supplies an epoch and its shared cancellation context atomically at handler entry. Closing registration advances the epoch and cancels the old context outside the registration mutex; reopening creates a fresh context rather than reviving old work. A setup captured while the gate is closed receives an already-canceled context. The existing TCP/UDP timeout budget is derived from that context, and the shared retry loop checks cancellation before every proxy attempt, including its first attempt. Its existing context-aware slowdown wait remains in place.

Cancellation is cooperative, not a join or a force-close guarantee. It begins when the bridge reaches `StopRegistrations` under the control mutex, not when a stop first queues behind parsing or configuration. Metadata processing and sniffing are not converted into context-aware operations. A proxy that ignores cancellation may still return later; its result must still pass the existing epoch-aware tracker admission, including rejection cleanup and failed-close retry ownership. A successfully admitted connection remains subject to the existing tracker cleanup rather than a new universal cancellation/relay contract. Generic retry callers now also honor a context that was already canceled before their first attempt.

Host regressions separately exercise cancellation-aware setup and deliberately context-ignoring late results, so cancellation does not replace the late-result closure defense. Fresh TCP/UDP traffic and the old-dial-blocked same-key TUN UDP regression remain required. Manager context lifecycle and retry call-count tests check stopped contexts, fresh reopening and rejection before another proxy attempt. Exact patch, manager and tunnel source digests are updated together; historical packaged-library hashes, upstream versions and all license/provenance/distribution gates are unchanged.

## Bounded ordinary setup drain, not complete kernel exit

Ordinary TCP dial/retry/early-handshake and asynchronous UDP dial setup acquire an epoch-checked lease immediately before entering setup. Closing registration prevents further acquisition and cancels the generation context. Releases are idempotent; pending setup ownership survives stop, timeout and reopening, so a non-cooperating adapter cannot disappear from the drain ledger. TCP pre-dial metadata/sniffing and synchronous UDP packet prechecks are outside this lease. The UDP asynchronous setup lease also spans its own sniff/metadata resolution and failure cleanup; these operations gain accounting, not forced cancellation. TCP relays, UDP sender/receive loops, NAT, DNS and provider workers remain outside the lease.

Android cleanup first closes the listener and captured trackers, allowing a registered early handshake to unblock, then waits at most two seconds for counted setup work. This is a setup-drain budget, **not an overall stop deadline**: listener/connection close, cancellation callbacks and existing other cleanup operations may still block. A drain timeout reaches the existing error/retry path and prevents replacement attachment from committing through failed cleanup. The next stop retries the same outstanding work; it does not abandon it or create a new worker to wait indefinitely. Adapters that ignore cancellation still rely on epoch rejection and ownership-aware late-result close.

After waiting, cleanup checks for trackers retained by a late rejected result's genuine close failure after the initial snapshot. Such newly retained ownership also makes stop fail and remains discoverable for the next cleanup; successful drain alone cannot hide that close failure. Success means only that the counted setup work completed and captured/late cleanup did not report unresolved ownership, not that all core goroutines exited.

No new native library is packaged or installed by this change. Upstream/dependency versions, historical packaged `.so` hashes, licensing/provenance/distribution approvals and release gates remain unchanged. Full kernel shutdown, pre-dial work cancellation, comprehensive non-TUN/TProxy generation isolation, DNS/provider cleanup and physical-device TUN/leak/battery acceptance remain outstanding. PR #133 must remain unmerged and unreleased.

## UDP sender queue ownership across close

The upstream sender's two cancellation selects allowed a Send already past its first check to enqueue after Close had canceled and drained the queue: the second select could randomly choose a writable queue over the canceled context. If its consumer had exited, that packet would never reach Drop. The connection-source adapter now uses a queue mutex to make the canceled-state check plus nonblocking enqueue atomic with Close cancellation. After that cancellation commits no sender can enqueue; full/rejected packets and drained packets are dropped outside the mutex, including reentrant callbacks. Concurrent closes and the consumer can dequeue distinct packets without duplicate queue ownership.

The regression group checks concurrent Send/Close without a masking second drain, concurrent closes, and Drop reentry from drain, full queue and already-closed admission. It is selected by the existing real-tunnel CI prefix. The adapter patch and exact connection-source hashes change together under the same five-source provenance checks; upstream pins and historical packaged-library hashes do not change.

This does not join Process, UDP receive loops, NAT or all core workers. A packet already taken by Process can remain in flight after Close, including resolution or forwarding. No overall stop deadline, complete non-TUN/TProxy generation isolation, DNS/provider shutdown, new `.so` packaging or physical-device TUN/leak/battery acceptance is claimed. The existing two-second setup-only wait and all licensing/release gates remain unchanged; PR #133 stays unmerged and unreleased.

## Dequeued UDP cancellation checkpoints, not a shutdown join

The adapted sender checks cancellation on dequeue before write-back, at packet-processing entry after write-back, after successful UDP resolution before mapping, and before writing after `Data` returns. `handleUDPToRemote` receives the sender context and also avoids a new deadline refresh when cancellation is observed after a write. Close/reentry never requires holding the queue mutex around write-back, resolution, data access, writes or release callbacks. A dequeued packet is released once by its consumer; queue cleanup never prematurely releases a packet still owned by a blocked callback.

Tests synchronize blocked resolver/write-back returns with Close, including a resolver that ignores cancellation, fresh successful forwarding, canceled selection, and reentrant Close from write-back, Data, WriteTo and Drop. They explicitly retain the behavior that an already-entered write may complete. A final context check is not atomic with a following callback or write: concurrent Close may return before that admitted operation completes, and there is no guarantee of zero post-Close traffic or full sender quiescence. No Process/receive-loop/core-wide join, DNS/provider cleanup, latest-library packaging or physical-device TUN/leak/battery acceptance is added. The setup-only two-second budget and upstream/license/version/historical-artifact/release gates are unchanged. ## Reverse UDP replies use registration-generation cancellation

`handleUDPToLocal` receives the registration context rather than the dial timeout context: normal setup completion must not cancel a healthy reply loop. The loop checks cancellation before reading, after deadline callbacks, after a read returns and after destination-NAT restoration before writing back. A late successful read after generation stop returns its buffer exactly once without forwarding. This does not join readers or write-back operations, cancel an individual sender's registration context, or force blocked reads to return. ## UDP forwarding cancellation no longer waits for reverse-reader cleanup

Normal UDP handlers construct senders with the registration-generation context. Thus cancellation checkpoints in outbound dequeue, resolution and pre-write processing observe stop even while the reverse reader has not returned to its deferred Close. The no-argument Background constructor remains compatible with independent callers. Process defers Close to serialize final queue draining against admission and run packet Drop callbacks outside locks; no cancellation callback worker is introduced.

Parent cancellation is cooperative, not a Process/reader join. A blocked callback or resolver retains its packet until returning, queued packets can remain until Process exits or another Close drains them, and already-entered writes may finish. ## TCP sniff waits also observe generation cancellation

TCP sniffing occurs before the ordinary setup lease. The handler now checks its captured registration context before entering sniffing and installs a scoped cancellation callback that closes the inbound connection while `TCPSniff` waits for data. The callback is removed when sniffing returns. A second context check rejects canceled reads even if they return valid buffered data and an apparently successful domain, before metadata resolution, the background peek or dialing can begin.

No manager or handler lock is held across the inbound `Close` callback. This relies on the normal `net.Conn` contract that `Close` unblocks `Read` and may run concurrently with it. A connection that ignores close is not forcibly interrupted; once it returns, its canceled result is still rejected. Removing the callback does not join an already-started close, and stop is not a complete TCP/sniffer/core exit barrier. Pre-sniff metadata resolution and external callbacks remain outside forced cancellation and setup accounting. Existing TCP sniff windows and the two-second setup drain are unchanged; full DNS/provider cleanup, comprehensive non-TUN generation isolation, new `.so` packaging and physical-device TUN/leak/battery acceptance remain incomplete. No merge or release is authorized by these host tests.

## TCP setup cancellation also covers early-handshake checkpoints

After setup admission, a separate scoped callback closes the inbound connection when the existing setup context is canceled by its generation or TCP timeout. This wakes a normal background peek that otherwise holds the early-handshake mutex. The handler checks cancellation after acquiring that mutex, after peeking buffered data, after an early write returns, and after the retry result before proceeding to relay. A canceled successful peek cannot initiate early writing; a write already in progress may finish, but its late successful result cannot consume inbound bytes or continue into relay once cancellation is observed. The callback is unregistered before successful setup transfers to relay ownership, and on every early return.

This callback only wakes the inbound read. It does not add a remote-write cancellation/join contract: tracked remote connections still use bridge snapshot cleanup, and a remote callback that ignores closure can retain setup debt. The last-check-to-call race remains, and callback removal does not join an already-entered Close. The ordinary background peek/relay and pre-dial metadata work are not newly included in a full exit barrier. The two-second setup budget, upstream pins, Android packaging and physical-device release gates remain unchanged. Current-revision verification is recorded in APP_PROGRESS; no merge or release is implied.

## Tokens observed while registration is stopped remain invalid after reopening

Every closed-to-open `StartRegistrations` transition now advances the registration epoch under the same admission mutex before creating its live context. `StopRegistrations` still invalidates the previous epoch and cancels outside the mutex. This prevents an epoch obtained from `Registration` or `RegistrationEpoch` while stopped (including a zero-value manager or repeated stops) from becoming valid when the gate reopens. Previously, its context remained canceled but the numeric epoch could be reused, allowing `BeginSetup` and tracker admission to disagree with that cancellation. Calling `StartRegistrations` while already open remains idempotent: it does not replace the epoch/context or discard outstanding setup ownership.

New manager regressions cover stopped-token setup rejection, reentrant rejected `JoinAtEpoch` cleanup, actual TCP/UDP tracker rejection and underlying socket closure, retained failed-close retry ownership, concurrent restart, and fresh-token/idempotent-start controls. This is an admission-generation fix, not a full shutdown barrier; it does not join already-entered callbacks or remote writes, alter the two-second setup wait, change legacy tracker constructor behavior, or complete DNS/provider shutdown, current-library packaging, or device acceptance. Exact patch/output digests are updated together; upstream pins and release gates remain unchanged.

## UDP Process exit retires sender-owned NAT independently of reverse reads

After a successful UDP dial, the forwarding goroutine defers `closeAllLocalCoon(key, sender)` around `sender.Process`. Thus Process termination on registration cancellation does not leave a canceled sender discoverable indefinitely merely because the reverse reader ignores cancellation or remains blocked. Reverse-reader cleanup remains independently idempotent with respect to entry ownership and cannot delete a replacement sender.

Tests use real TUN and TProxy handler forwarding, retain the old reverse read, observe old entry/socket retirement, then reopen and pass actual bytes through a fresh sender before and after old-owner cleanup. ## TProxy local socket creation is bound to its captured NAT entry

The earlier Process-owned cleanup could miss a local socket whose creator was still running: address-based publication after retirement could either find no entry and leave the new socket unowned, or attach it to a replacement sender. The adapted TProxy creation path now calls `GetOrCreateLocalConn`, capturing the original entry before invoking its socket maker. Per-remote completion channels replace the old condition-variable wait, avoiding missed broadcasts and unlocking errors. Makers run outside table/entry locks, and a retirement signal wakes followers even when the maker ignores cancellation. Successful publication and retirement are serialized by the entry mutex; an already-published socket is included in cleanup, while a result arriving after retirement is closed by its creator and returned as `net.ErrClosed`. A failed maker can be retried and cannot transfer a non-nil failed socket to callers.

This is a nonblocking ownership protocol, not a creator join. An uncooperative maker can keep running after stop, but must close its result on returning. An old write-back callback that has not captured an entry before retirement can still observe a newly created entry; this does not establish complete generation isolation, synchronous exit, or zero-loss immediate restart. TUN generation keys and TProxy bare keys remain unchanged; the legacy `constant.NatTable` interface is unchanged, and the adapted TProxy path fails closed for an implementation lacking the new ownership method. DNS/provider cleanup, current `.so` packaging, physical-device TUN/leak/battery acceptance, and the two-second setup budget remain separate release gates. The newly adapted `listener/tproxy/packet.go` joins the pinned-source, reviewed-output and artifact-provenance checks rather than bypassing them.
